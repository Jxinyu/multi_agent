# 检索准确性与性能优化

日期：2026-08-12

## 结论

在线混合检索已从“Milvus、Neo4j 分别重排后按原始分值去重”调整为：

1. Milvus 与 Neo4j 并发召回授权范围内的候选。
2. 各后端内部按自身分值排序，使用 RRF 按名次融合候选。
3. 对融合候选执行一次全局 BGE 重排，最终顺序只使用同一次模型打分。
4. 重排后再次执行租户、owner 和 ACL 校验。
5. 按总字符数和单文档切片数构造上下文。

该设计修复了两个问题：Milvus 与 Neo4j 的原始分值不在同一量纲，不能直接比较；旧链路会执行两次 BGE 重排，既增加计算量，也只能在各自后端的局部候选中排序。

## 为什么不直接输出 RRF 排序

RRF 适合合并不同检索器的候选，因为它只依赖名次，不比较不同后端的原始分值。但 RRF 只能表示多个检索器的排序共识，不能判断 query 与文本的细粒度语义相关性。

MultiHop-RAG 500 条公开样本的已有实验验证了这一点：

| 方案 | Recall@10 | 相对向量基线 |
| --- | ---: | ---: |
| 文档级向量检索 | 79.73% | 基线 |
| 直接输出 Hybrid RRF | 79.10% | -0.79% |
| RRF 候选后做自适应重排 | 86.85% | +8.93% |

因此，在线链路仅使用 RRF 缩小和融合候选集，最终排序交给同一个 BGE Cross-Encoder。RRF 的单元测试验证跨后端共同命中的候选能进入前列，但不将该测试当作公开准确率实验。

## 公开准确率证据

项目的检索准确率主实验仍采用公开 MultiHop-RAG，金标是官方 `evidence_list.title`，指标为证据文档 Recall@10：

| 实验范围 | 基线 | 当前实验方案 | 结果 |
| --- | --- | --- | ---: |
| 500 条样本 | 文档级向量检索 | 自适应候选重排 | 79.73% 到 86.85%，相对提升 8.93% |
| 全部 2255 条可评估 query | 文档级向量检索 | chunk 召回与 source coverage 重排 | 79.84% 到 90.82%，相对提升 13.75% |
| train 1300 / dev 200 / holdout 755 | 文档级向量检索 | chunk、BM25 与 LambdaMART | 78.97% 到 96.61%，相对提升 22.34% |

边界：`+22.34%` 属于监督式 LambdaMART 离线方案。当前在线实现是 RRF 候选融合与 BGE 重排，不能宣称在线链路已经达到 96.61%。上线前应在企业文档金标集上按相同 query、ACL 和候选上限做离线回放或 A/B 验证。

## 本机效率基准

脚本：`evals/rag/benchmark_runtime_rerank.py`

命令：

```powershell
conda run -n rag python evals/rag/benchmark_runtime_rerank.py --iterations 3 --per-backend 40 --overlap 20 --fusion-limit 40
```

环境为 Windows 11、本地 `bge-reranker-v2-m3`、`top_n=8`。模型加载和一次预热不计时；新旧方案使用同一查询和候选文本，并交替运行以降低执行顺序偏差。

运行编号：`runtime_rerank_20260812_032257`。

| 指标 | 旧方案：两后端分别重排 | 新方案：融合后全局重排 | 变化 |
| --- | ---: | ---: | ---: |
| BGE 调用次数 | 2 | 1 | -50.00% |
| query-document 输入对 | 80 | 40 | -50.00% |
| 中位重排耗时 | 16.6313 s | 8.2728 s | -50.26% |

该数字仅衡量本机 BGE 重排阶段，不包含 Milvus、Neo4j、网络和答案生成，也不等同于生产 P95。生产性能应通过 `/metrics` 中的检索总耗时、融合候选量和重排耗时直方图统计。

## 在线边界与监控

默认配置：

| 配置 | 默认值 | 作用 |
| --- | ---: | --- |
| `RETRIEVAL_CANDIDATE_TOP_K` | 30 | 每个授权过滤分支的候选数 |
| `RETRIEVAL_BACKEND_CANDIDATE_LIMIT` | 40 | 单后端去重后的候选上限 |
| `RETRIEVAL_FUSION_CANDIDATE_LIMIT` | 40 | 进入 BGE 的融合候选上限 |
| `RERANKER_TOP_N` | 8 | 最终保留的重排结果数 |
| `RETRIEVAL_TIMEOUT_SECONDS` | 20 | 单后端召回和重排等待上限 |
| `RETRIEVAL_MAX_CONTEXT_CHARS` | 12000 | 输入回答模型的参考资料字符上限 |
| `RETRIEVAL_MAX_CHUNKS_PER_DOCUMENT` | 2 | 防止单文档占满上下文 |

Prometheus 指标：

- `rag_upper_retrieval_duration_seconds`：完整检索链路耗时。
- `rag_upper_retrieval_candidates`：每个后端返回的候选数。
- `rag_upper_retrieval_fused_candidates`：进入 BGE 的融合候选数。
- `rag_upper_retrieval_rerank_duration_seconds`：全局重排耗时。
- `rag_upper_retrieval_results`：重排后的结果数。

超时会抛出明确的 `RetrievalTimeoutError`，不会把异常后端静默伪装成成功。某个后端正常返回空候选时，融合链路仍可使用另一后端的合法候选。BGE 在专用单工作线程中执行，避免阻塞 FastAPI 事件循环和占满公共线程池；这也意味着单进程内的重排请求会排队，正式容量规划必须压测并按模型吞吐决定副本数。

## 验证范围

自动化测试覆盖：

- 双后端候选并发召回。
- 不同分值量纲下的 RRF 共识排序。
- 融合候选只执行一次全局重排。
- 后端召回和重排超时显式失败。
- 重排不阻塞事件循环。
- 重排后授权复核。
- 总上下文长度和单文档切片数限制。

仍需用真实企业数据验证：Recall@K、nDCG@K、答案忠实度、权限过滤后的无结果率、检索 P95/P99 和高并发排队时间。
